# i18n — Español como idioma principal + switch de idioma

**Objective**: Add Astro's native i18n routing with Spanish as the default locale at the URL root, translate the whole site to Spanish, keep English available under `/en/`, and add a language switch in the header.

**Branch**: N/A — the project is not a git repository, so work-unit commits and PR slices are not possible. Flagged to the user.

**Delivery**: N/A (no git). Would be `ask-on-risk` once a repo/remote exists — the authored-lines forecast is well over 400.

**Test runner**: none installed (no test script, no framework). Proportional checks: `npm run build` + served/built HTML assertions per locale.

## Specs

### S1 — Native i18n routing, Spanish at the root
`i18n` config in `astro.config.mjs` with `defaultLocale: "es"`, `locales: ["es","en"]` and `prefixDefaultLocale: false` (Astro's default).

- Spanish at `/` and `/hire-me` (no prefix).
- English at `/en/` and `/en/hire-me`.
- Default-locale pages stay in `src/pages/`; English pages live in `src/pages/en/`.
- Config shape verified against the installed `astro@7.3.8` (`node_modules/astro/dist/core/config/schemas/base.d.ts`): `defaultLocale`, `locales`, `routing.prefixDefaultLocale`, `routing.redirectToDefaultLocale`, `routing.fallbackType`.

**Acceptance**: `npm run build` emits `dist/index.html`, `dist/hire-me/index.html`, `dist/en/index.html`, `dist/en/hire-me/index.html`.

### S2 — Translations are NOT native: own dictionary module
Astro ships i18n *routing* only; there is no built-in translation API. Per the official recipe, own the strings in `src/i18n/`:

- `src/i18n/ui.ts` — `defaultLang`, `languages`, `Locale` type, flat dot-key UI dictionary (`es` as the source of truth, `en` typed as `Record<keyof typeof es, string>` so a missing key is a compile error).
- `src/i18n/content.ts` — locale-keyed structured content (profile paragraph, stack, services, 6 experiences, education) typed with an explicit `SiteContent` shape.
- `src/i18n/utils.ts` — `isLocale`, `getLocale`, `useTranslations(locale)` (falls back to the default locale on a missing key), `stripLocale(pathname)`.

**Acceptance**: a page rendered in either locale shows every string in that locale; no component holds a hardcoded user-facing English literal.

### S3 — Every user-facing string is translated
Full inventory translated (11 components + 4 pages + Layout): layout metadata, header nav, hero (eyebrow, h1 lines, intro, both CTAs, card labels), services (heading, intro, 3 cards), contact form (heading, intro, 3 labels, 3 placeholders, submit), about CTA, footer, hire hero, profile, experience gallery, education.

- UI/structure copy lives in `ui.ts`; resume data (profile text, 6 experiences, education, services cards) lives in `content.ts`.
- Tech names in the stack (`React`, `Tauri v2`, `CI/CD`, …) stay untranslated — they are proper nouns.
- Register: **neutral Spanish** (stated default; the user can request Rioplatense afterwards).

**Acceptance**: no English-only sentence appears in the Spanish pages, and no Spanish sentence in `/en/`.

### S4 — Language switch in the header
A link-based switch (real URLs, not a client-side toggle) in `SiteHeader.astro`.

- Links to the *same page* in the other locale: derived from the current path with `stripLocale` + `getRelativeLocaleUrl`.
- Active locale is visually marked (same underline treatment as the active nav item).
- `aria-label` from the dictionary; `hreflang` attribute on the alternate link.

**Acceptance**: `/` → switch → `/en/`; `/hire-me` → `/en/hire-me`; `/en/hire-me` → `/hire-me`. The nav links themselves also stay inside the current locale (`/en/#services`, `/en/hire-me`).

### S5 — Per-locale `lang` attribute and hreflang alternates
- `<html lang>` must be `es` or `en` per page.
- `ClientRouter` replaces `<body>` completely but **not** `<html>` (verified in the Astro docs' client-side navigation sequence), so `lang` survives stale across client-side navigation. Fix: set `document.documentElement.lang` from the URL inside the existing `astro:page-load` handler in `Layout.astro`.
- `rel="alternate" hreflang="es|en"` links in the head, plus `x-default` → Spanish.
- Absolute hreflang needs `site` in the Astro config, which is unset (no domain yet): emit relative alternate URLs and note it.

**Acceptance**: built HTML has the right `lang`; after client-side navigation between locales the attribute is corrected at runtime.

### S6 — Hero typewriter must not depend on locale-specific measurements
The h1 currently reserves a fixed height (`h-[2.85em] md:h-[1.9em] lg:h-[2.85em]`) measured for the English text. Spanish wraps differently, so a per-locale magic number would be wrong again on any copy or font change.

- Replace the magic height with a locale-agnostic sizer: an invisible copy of the full text reserves the exact height; the animated copy is absolutely positioned over it so typing never affects layout.
- Accessible/SEO text is preserved via an `sr-only` copy; the animated layer is `aria-hidden`.
- The typewriter script keeps reading `textContent` from the DOM, so it picks up the locale's text with no change.
- Drop the `h-*`/`md:h-*`/`lg:h-*` classes on `.hero-title`.

**Acceptance**: on `/` and `/en/` the h1 height equals the full-text height, is identical while the text types/deletes, and nothing below it moves.
